# P0-3 · P0-4 쉬운 설명 (커널 메모리 보호 켜기)

> 대상 iso-light-k0 1.0.0 릴리즈의 마지막 보안 숙제
> 목적 "커널 메모리 보호가 왜 꺼져 있고 어떻게 켜는가"를 코드 몰라도 이해하게 정리
> 상태 착수 전 (QEMU 로컬/VM 에서 개발·검증 가능, 아래 5번 참고)

## 한 줄 요약

지금 커널은 "코드는 못 고치게, 데이터는 실행 못 하게" 막는 기본 보호 장치가 꺼진 무방비 상태다. 켜는 스위치는 이미 만들어져 있지만, 그냥 켜면 커널이 즉사한다. 그래서 켜기 전에 커널을 "정식 주소"로 이사시키는 사전 공사가 필요하다.

## 1. 무슨 문제인가

안전한 커널은 메모리를 이렇게 나눠 지켜야 한다.

- 코드 영역 -> 실행만 되고 수정은 불가 (누가 몰래 코드를 바꿔치기 못 함)
- 데이터·스택 영역 -> 수정은 되지만 실행은 불가 (데이터를 코드처럼 몰래 실행 못 함)

이 원칙을 W^X(쓰기 XOR 실행, 둘 중 하나만)라고 부른다. 공격자가 코드를 조작하거나 데이터를 악성 코드로 실행하는 걸 막는 가장 기본적인 방어다.

문제는 지금 이 보호가 **전부 꺼져 있다**는 것이다. 커널의 모든 메모리가 "읽기·쓰기·실행 다 됨" 상태로 돌아간다. 방어벽이 세워지긴 했는데 스위치를 안 올린 셈이다.

- P0-3 (H1) 보호 스위치 자체가 꺼져 있음
- P0-4 (H2) 스위치를 켜도 뒷문이 하나 남음 (아래 3-5 참고)

## 2. 왜 아직 못 켜나

좋은 소식부터. 스위치는 이미 만들어져 있다 (`src/arch/x86_64/mmu.rs`의 `activate()` 함수, CR3 재로드). 없어서 못 켜는 게 아니다.

나쁜 소식. 이 스위치를 켜는 순간 커널이 그 자리에서 죽는다(즉시 재부팅, triple fault).

왜 그런지 비유로.

- 지금 커널은 "임시 주소"에 살고 있다 (물리 주소 `0x100000`에 그대로 링크됨)
- 스위치를 켜면 커널은 새 "보안 지도"(새 페이지 테이블)를 쓰기 시작한다
- 그런데 그 새 지도에는 커널이 지금 살고 있는 임시 주소가 안 적혀 있다
- 결과 스위치를 켠 다음 줄을 실행하려는 순간, 커널이 자기 집 주소를 못 찾고 죽는다

그래서 이전 개발자가 스위치를 일부러 주석 처리해 꺼뒀다 (`src/arch/x86_64/kernel_start.rs`의 11단계, 505-514행에 이유가 코드 주석으로 적혀 있음).

## 3. 어떻게 고치나

핵심은 "커널을 임시 주소에서 정식 주소로 이사시키는 것"이다. 이사가 끝나면 새 지도에도 커널 주소가 제대로 적혀서, 스위치를 켜도 죽지 않는다.

할 일 목록 (QEMU 에서 순서대로, 단계마다 부팅으로 확인)

- [ ] 1. 커널 이사 (higher-half 재배치)
  - 링커 스크립트(`linker.ld`)를 고쳐 커널을 정식 고주소(`0xFFFF_FFFF_8000_0000`)에서 돌게 만든다
  - 이게 제일 크고 위험한 부분이다. 조금만 어긋나도 부팅이 아예 안 된다
- [ ] 2. NX 실효화 (하드웨어 스위치)
  - `IA32_EFER.NXE`를 켠다 (`mmu.rs:546`의 TODO). 안 켜면 "실행 금지" 표시를 CPU가 무시한다
- [ ] 3. 보호 스위치 켜기 (activate)
  - `kernel_start.rs`의 주석 처리된 `activate()` 호출을 살린다
- [ ] 4. 뒷문 막기 (P0-4 / H2)
  - `build_linear_map()`(`mmu.rs:613`)이 지금은 커널 코드 영역까지 "수정 가능"으로 이중 매핑한다 (634-636행이 전부 WRITABLE)
  - 스위치를 켜도 이 뒷문으로 코드를 고칠 수 있으므로, 커널 코드·상수 영역만 "읽기 전용·실행 금지"로 바꿔 막는다
- [ ] 5. 화면 출력 주소 전환
  - 이사 후에는 화면 버퍼(VGA) 주소도 새 지도 기준으로 바꿔야 한다 (`kernel_start.rs:493-495`의 주석 처리된 `vga::update_base()`)
- [ ] 6. 확인용 부팅 메시지 추가
  - 부팅 화면에 "W^X 보호 켜짐" 한 줄을 찍어 눈으로 확인할 수 있게 한다

건드리는 파일은 크게 4개다.

- `linker.ld` (커널 이사)
- `src/arch/x86_64/mmu.rs` (NXE 켜기, 뒷문 막기)
- `src/arch/x86_64/kernel_start.rs` (스위치 켜기, 화면 주소 전환, 확인 메시지)
- `src/arch/x86_64/boot_stub.rs` (이사 과정의 초기 진입 전환, 필요 시)

## 4. 다 됐는지 어떻게 확인하나 (완료 판정)

"코드를 짰다"로는 부족하다. 실제로 부팅시켜서 보호가 진짜 작동하는지 눈으로 봐야 한다.

- [ ] 커널 코드 영역에 일부러 쓰기를 시도했을 때, 진짜로 page fault로 차단되는 걸 1건 실증
- [ ] 뒷문(linear map)으로 코드에 쓰기를 시도해도 차단되는 걸 실증
- [ ] objdump로 실행 금지(NX) 비트가 실제로 박혔는지 실측
- [ ] 부팅 화면에 "W^X 켜짐" 메시지가 뜨는지 확인

(원문 기준 `RELEASE-READINESS.md`의 P0-3·P0-4 완료 판정 항목)

## 5. QEMU(TCG)에서 테스트할 수 있나 (중요)

**할 수 있다.** 흔한 오해가 하나 있어 짚는다. "QEMU/TCG는 하드웨어 난수가 없어 부팅이 멈추니 P0-3/P0-4도 검증 못 한다"는 말은 틀렸다.

핵심은 부팅 순서다.

- 우리가 켜려는 보호(activate + W^X)는 **11단계** (`kernel_start.rs:505`)
- QEMU/TCG가 멈추는 엔트로피 초기화는 **12단계** (`kernel_start.rs:520`)

즉 W^X 집행은 엔트로피가 필요해지기 **전에** 끝난다. 뒤에서 커널이 멈추든 말든 상관없다.

게다가 QEMU/TCG가 못 하는 건 하드웨어 난수(RDRAND) 하나뿐이고, **페이지 테이블·NX 비트·페이지 폴트(#PF)는 TCG가 정확히 흉내 내는 부분**이다. 그래서 4번의 완료 판정("코드에 쓰기 -> page fault로 차단")을 QEMU에서 그대로 관찰할 수 있다. activate 직후 즉사(triple fault) 여부도 스모크 하네스가 세는 재부팅 횟수로 바로 보인다.

오히려 이사 공사(higher-half 재배치)는 "부팅 -> 죽음 -> 고침 -> 재부팅" 반복이 정상인데, TCG는 재부팅이 빨라 이 작업에 잘 맞는다.

주의할 점은 "테스트를 못 해서"가 아니라 단지 **변경이 크고 델리케이트해서**다. 한 번 삐끗하면 부팅이 아예 안 되므로, 단계마다 부팅으로 확인하며 조금씩 나아가야 한다.

## 6. 어디서 실행하나

- **개발·기능 증명** QEMU/TCG(맥 로컬 또는 리눅스 VM)로 충분하다. 3번 순서대로 진행하고 단계마다 부팅시켜 4번 판정("쓰기 -> 폴트")을 채운다
- **최종 릴리즈 도장(선택)** 보안상 실물 CPU(KVM x86 또는 실기)에서 한 번 더 확인하면 belt-and-suspenders가 된다. 필수는 아니고, 페이징·NX는 TCG가 가장 충실히 흉내 내는 영역이라 기능 증명 자체는 QEMU로 성립한다

참고로 하드웨어 난수가 진짜 필요한 건 **P1(엔트로피·암호 런타임 마커)** 쪽이다. 이건 P0-3/P0-4와 별개 항목이며, 그쪽만 KVM/실기가 필요하다. 두 항목이 문서상 같은 "런타임 보류" 칸에 묶여 있어 혼동하기 쉬우니 구분한다.

## 참고 (현재 진행 상황)

- 직전 작업(GAP-1)은 이미 안전하게 종결됨. arch 전용 코드 정리로 HAL-06 게이트가 초록불로 돌아왔고, 양쪽 CPU 빌드·부팅 무회귀 확인 완료
- P0-3·P0-4는 이 문서로 착수 준비만 마친 상태 (코드 변경은 아직 없음)
